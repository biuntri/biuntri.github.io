# commit

変更を論理単位で作業ブランチにコミットし、その作業ブランチを push する。main は公開中の本番なので、main へ直接コミットや push をしない（main には PR で入れる）。PR はこのスキルでは作らない（PR 用の別スキルで扱う）。

## 手順

1. 状態を確認する。次の4つは独立しているので並列で実行する。
    - `git status`
    - `git diff HEAD`
    - `git log --oneline -10`（直近の文体に合わせるため）
    - `git branch --show-current`（現在のブランチの確認。detached HEAD のときは何も出ない）

    detached HEAD なら、コミットも push もせずにそう報告して終わる。main 上なら、下の「main 上にいたとき」に従う（手順3の後・手順4の add の前に切る）。
2. 変更の出どころを分ける（下の「セッション外の変更の扱い」）。確認が必要なものがあればここで確認し、コミット対象を決める。main 上なら、ブランチ名の確認もここで行う（下の「main 上にいたとき」参照）。対象がなくなったら、コミットも push もせずにそう報告して終わる。
3. コミット対象を論理単位に分ける。無関係な変更が混ざっていたら複数コミットに分ける。分けるかどうかで迷ったら、1つの目的で説明できるかで判断する。
4. コミットしてよいファイルを `git add <ファイル名>` で名指しして追加する。`git add -A` や `git add .` は使わない。意図しないファイル（秘密情報、生成物、セッション外の変更）を巻き込まないため。
5. `git commit` する。フックに拒否されたときは、`--no-verify` で回避せずに、拒否の内容を報告して止まる。
6. 作業ブランチを `git push` する（自動。確認は取らない）。上流ブランチが未設定なら `git push -u origin <ブランチ名>` を使う。手順1の `git status` の出力に上流の追跡情報（「Your branch is ... 'origin/<ブランチ>'」の行）がなければ、未設定とみなす。その行があっても、追跡先の `<ブランチ>` が現在のブランチ名と違うとき（例: `git switch -c foo origin/main` で切った `foo` が `origin/main` を追跡している）は未設定とみなし、`git push -u origin <現在のブランチ名>` を使う。そのまま `git push` すると、名前の不一致で失敗したり、main への push を試みて pre-push フックに拒否されたりするため。main 上から手順4の前に切ったブランチは、上流が未設定として扱う（手順1の `git status` は main の追跡情報なので当てはまらない）。
7. 完了後、コミットのハッシュと1行目だけを短く報告する。確認のうえ対象から外したファイルがあれば、作業ツリーに残っていることを1行で添える。

## main 上にいたとき

main にはコミットしない（`.githooks/pre-commit` も main へのコミットを拒否する）。手順1で main 上と分かったら、次のようにする。

- 手順2で、作業ブランチ名を `AskUserQuestion` で確認する。
    - `multiSelect: false`（1つだけ選ぶ形式）にする。
    - 選択肢は次の順に並べる。
        1. 上から、変更内容から考えた提案名を1つ以上並べる。先頭の提案名に「(Recommended)」を付ける。各選択肢の説明には、その名前にした理由（何の変更か）を短く書く。
        2. 一番下に「ブランチを切らない」を置く。説明は「コミットも push もせずに終える」。
    - 選択肢は4つまでなので、提案名は最大3つにする。
    - 別の名前にしたいときは「Other」に自由記述してもらう。自由記述があればその名前を使う。どの名前か曖昧なら、同じ形式でブランチ名の質問だけを出し直す（提案名の選択肢と、一番下の「ブランチを切らない」を含める）。ファイル選択の答えはすでに得ているので、もう一度は聞かない。
    - ブランチ名の自由記述と、ファイル選択の「Other」の自由記述が両方とも曖昧だったときは、聞き直しも1回の `AskUserQuestion` にまとめる。質問は最初の確認と同じ順序と形式で並べる（ブランチ名の質問を先、ファイル選択の質問を後）。確認を2回に分けないためで、下のファイル選択をまとめる方針と同じ理由による。
- 提案名は、手順1の diff から、セッションで変更したものを中心に決める。ファイル選択の確認と同時に聞くため、コミット対象が決まる前に提案名を決める必要がある。
- 手順2でセッション外の変更の確認（ファイル選択）も必要なときは、ブランチ名の質問とファイル選択の質問を1回の `AskUserQuestion` にまとめる（1回の呼び出しで4問まで）。確認を2回に分けると、ユーザーの手間が増えるため。
    - 質問は、ブランチ名の質問を先、ファイル選択の質問を後に並べる。
    - ファイル選択の質問を2つ以上に分ける場合も、ブランチ名の質問と合わせて4問を超えないようにする。超えるときは、ファイル側の質問をまとめて減らす。
    - ファイル選択の確認が不要なときは、ブランチ名の質問だけを出す。
- 了承を得たら（提案名のどれかを選ばれたとき、または「Other」に曖昧でない名前を自由記述されたとき）、手順3の後・手順4の add の前に `git switch -c <ブランチ名>` で作業ブランチを切り、そのブランチでコミットする。手順1・2の時点ではまだブランチを切らない。
- 了承が得られなければ、コミットも push もせずにそう報告して終わる。質問自体を拒否されたとき、ブランチ名を選ばず「Other」の自由記述もせずに返されたとき、「ブランチを切らない」を選ばれたときが、これに当たる。

## セッション外の変更の扱い

作業ツリーには、セッションを始める前からあった変更や、ユーザーが手で編集した途中の変更が残っていることがある。それを黙ってコミットして push すると取り消しにくいので、自分で変更したと分かるものだけを自動でコミットし、それ以外はユーザーに決めてもらう。

`git status` に出たファイルを次の3つに分ける。

1. **セッションで変更したもの** → そのままコミット対象にする。
    - この会話で Edit / Write / NotebookEdit を使ったファイル
    - Bash（`sed`、リダイレクト、`mv`、`rm` など）で作成・変更・削除したファイル
    - サブエージェント（builder、docs-writer など）に編集させたファイル
2. **セッション中にユーザーが扱いを指示したもの** → 指示に従い、改めて確認しない。
    - 例: 「.claude/ もまとめてコミットしておいて」なら含める。「.githooks/pre-push はまだコミットしないで」なら含めない。
    - 指示がどのファイルを指すか曖昧なときは 3 として扱う。
3. **それ以外**（出どころが分からないものを含む） → コミット前に確認する。

判断の材料は会話の履歴と、システムコンテキストの `gitStatus`（セッション開始時点の状態）。

- 開始時点の `gitStatus` にすでに出ていたファイルをこのセッションでも編集した場合、diff に自分が書いていない部分が混ざっているおそれがある。diff がすべて自分の変更だと確かめられなければ 3 として扱う。
- 会話が要約されていて、自分が変更したかはっきりしないときも 3 として扱う。迷ったら確認する側に倒す。

確認には `AskUserQuestion` を使い、「コミットに含めるファイル」を選んでもらう。毎回同じ形と並びで出すと、ユーザーが迷わずに選べる。そのため、形式は次のとおりに固定する。

- 対象が1件だけでも、必ず `multiSelect: true`（チェックボックス式）にする。
- 選択肢は次の順に並べる。
    1. 先頭は常に「すべてコミットしない」にする。説明は「どれも add せず、作業ツリーに残す」。
    2. その後に、コミットに含める候補を `git status` に出た順で並べる。各選択肢には、ファイル名と変更の概要（追加／変更／削除、何についての変更か）を書く。
- 選択肢は1つの質問につき4つまでで、そのうち1つは「すべてコミットしない」に使う。候補が3件を超えるときは、ディレクトリや目的でまとめて3つ以内にする。
- 目的が4つ以上あって3つ以内にまとめられないときは、質問を2つ以上に分けてよい（1回の `AskUserQuestion` で4問まで）。main 上にいたときは、ブランチ名の質問と合わせて4問以内にする（「main 上にいたとき」を参照）。目的の違うものを無理に1つの選択肢にまとめると、一部だけコミットするという選び方ができなくなるため。分けるときは次のようにする。
    - 各質問に、その質問で扱う候補だけを入れる。どの質問も先頭は「すべてコミットしない」にする。
    - 各質問の「すべてコミットしない」は、その質問の候補だけに効く。
    - 答えは質問ごとに、下のルールで扱う。

答えは次のように扱う。

- 「すべてコミットしない」だけを選んだとき、または何も選ばずに返したとき → どれもコミットしない。
- 「すべてコミットしない」とファイルを両方選んだとき → 答えが矛盾しているので、何も add せずにもう一度確認する。
- ファイルだけを選んだとき → 選ばれたファイルをコミット対象にする。
- 「Other」に自由記述があったとき → その指示に従う。どのファイルを指すか曖昧なら、コミットせずに聞き直す。

選ばれなかったファイルは add せず、作業ツリーにそのまま残す。`git stash`、`git checkout`、`git restore` などで消したり退避したりしない。ユーザーの作業途中のものかもしれないため。

ユーザーが選んだものでも、下の「コミットしてはいけないもの」に当たるものは追加せず、理由を伝える。

## コミットしてはいけないもの

次に該当するファイルは追加せず、除外したことをユーザーに伝える。

- `.env`、`credentials.json`、鍵、トークンなど秘密情報の疑いがあるもの

## メッセージの書き方

- 日本語で書く。
- 1行目は短く（目安50字前後）、末尾に「。」は付けない。何をしたかが分かる体言止めや動詞止めにする。
    - 例: `pre-push フックに削除 push の拒否を追加`
    - 例: `CLAUDE.md に公開方法を追記`
- `feat:` `fix:` などのプレフィックスは付けない。
- 本文は原則省略する。次の2つの条件を両方満たすときだけ付ける。
    - 1行目だけでは「なぜその変更をしたか」が伝わらない。
    - 1行目で説明しきれず、後から読む人が迷う理由や注意点がある。
- 本文を付けるときは、1行目の後に空行を挟み、理由や背景を数行で書く。変更内容の羅列はしない（diff を見れば分かるため）。
- 本文を省くために、別々の目的の変更を1コミットにまとめない。粒度は「1つの目的 = 1コミット」を保ち、そのうえで本文が要らなくなるように1行目を具体的に書く。
- 末尾に、システムのリマインダーで指定された Co-Authored-By などの行があれば、そのまま付ける。

## push が失敗したとき

原因（認証、リモートが先に進んでいる、フックによる拒否、ネットワークなど）を報告して止まる。`--force` や `git reset --hard` で解決しない。フックに拒否されたときも `--no-verify` で回避しない。リモートが先に進んでいる場合は、`git pull --rebase` を提案するだけにして、実行はユーザーの返事を待つ。
